# 題材企画: `String.split`が末尾の空列を捨て、CSVインポートが任意列を拒否する

## 対象

| 項目 | 内容 |
| --- | --- |
| 対象言語 | Java 21 |
| 対象読者 | Javaの文字列処理で区切り形式を扱い、`split`を標準的なCSV風入力へ使う中級者 |
| 難易度プロファイル | 実践・上級 |
| 選定理由 | 末尾だけが空の入力は見た目では通常の3列に見える一方、`String.split(String)`の既定limitによって列数が変わる。業務上の受理結果、保存された最終状態、標準ライブラリのトークン列を分けて観測し、入力妥当性・正規表現・split契約という競合仮説を比較できる。 |
| 実行基盤 | Maven、Java 21、JUnit Jupiter 5.11.4 |
| フレームワーク非依存性 | 原因は`java.lang.String.split`のlimitに関する標準ライブラリ契約である。HTTP、DI、DB、ORM、CSVライブラリには依存せず、固定文字列だけで再現する。 |

## 学習する契約

> 入力`"SKU-17,Tea,"`に対して、期待する結果は「任意のメモが空の`ProductImportRow("SKU-17", "Tea", "")`を受理・保存する」ことだが、バグ状態では`REJECTED`となり、受理済み行が空で拒否件数が`1`になる。

### 対象の直接原因

`String.split(",")`は既定のlimit `0`と同じであり、末尾の空文字列を結果配列から破棄する。したがって、末尾の任意列が空の入力は二列に短縮され、列数検証で拒否される。

### 対象外

このラボはRFC 4180準拠のCSV（引用符、カンマを含む値、改行、文字コード）、CSVライブラリの選定、ストリーミングI/O、ファイルの原子性を扱わない。固定のカンマ区切り・引用符なし・三列という狭い入力形式における、末尾空列の保持だけを扱う。

## 再現設計

| 要素 | 決定 |
| --- | --- |
| 公開境界 | `CsvImportService#importLine(String)`と、受理済み行・拒否件数を読む公開API。 |
| 入力・初期状態 | 空のインメモリ状態へ、固定入力`"SKU-17,Tea,"`を一度与える。 |
| Redの観測 | `ImportOutcome.ACCEPTED`を期待するが、バグ状態では`ImportOutcome.REJECTED`となる。 |
| 最終観測 | `acceptedRows()`に空メモの行が一件残り、`rejectedCount()`が`0`であることを別々に検証する。通常の非空メモ行は引き続き受理されることも検証する。 |
| 決定性 | 時刻、乱数、ファイル、ネットワーク、並行処理、`sleep`を使わず、固定文字列とインメモリ状態だけを使う。 |
| 固定状態の検証コマンド | `mvn --batch-mode clean test` |
| バグ状態の確認コマンド | `git checkout 4488fb6`後に`mvn --batch-mode test -Dtest=CsvImportServiceTest` |

## 仮説

| 仮説 | どう検証または除外するか |
| --- | --- |
| A: 末尾メモが空の入力は業務ルール上不正である | 同じサービスが非空メモを受理することと、契約テストが空文字メモの受理を明示することを比較する。 |
| B: 区切り記号の正規表現解釈によりカンマ自体が誤って扱われる | カンマを二つ含む固定入力で、`split(",")`と`split(",", -1)`のトークン列を比較する。 |
| C: `String.split`の既定limitが末尾の空トークンを捨てる | 両方のsplit結果の長さと内容を観測し、標準ライブラリの公式仕様と照合する。 |

## 予定する履歴

| 順序 | コミットの目的 | 期待する状態 |
| --- | --- | --- |
| 1 | CSV末尾空列の受理失敗を再現する | 対象テストが`ACCEPTED`期待・`REJECTED`実際のアサーション差分で失敗する。 |
| 2 | 末尾空列を保持してCSV行を解析する | 同じ検証が成功し、全体も成功する。 |
